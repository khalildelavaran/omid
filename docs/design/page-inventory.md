# فهرست طراحی و معیار پذیرش صفحات سامانه امید

این سند مبنای تکمیل طراحی رابط کاربری است. وجود یک صفحه در این فهرست به معنی تکمیل پیاده‌سازی یا اتصال عملیاتی آن نیست؛ وضعیت هر مورد باید با مشاهده رابط و آزمون کد تأیید شود.

## اصول مشترک طراحی

- زبان رابط فارسی، راست‌چین و با ارقام فارسی در نمایش؛ شناسه‌های فنی و شماره پرونده‌ها خوانا و قابل کپی باقی بمانند.
- ساختار ثابت شامل منوی کناری، نوار بالایی، عنوان صفحه، مسیر راهنما و محتوای صفحه باشد.
- دکمه اصلی هر صفحه از نظر جایگاه و ظاهر مشخص باشد؛ عملیات خطرناک یا برگشت‌ناپذیر از عملیات عادی متمایز شوند.
- تمام صفحات حالت بارگذاری، خطا، فهرست خالی، نتیجه جست‌وجوی خالی و موفقیت عملیات داشته باشند.
- فرم‌ها برچسب واضح، فیلد اجباری مشخص، اعتبارسنجی قابل فهم و جلوگیری از ارسال چندباره داشته باشند.
- جدول‌ها در موبایل اسکرول افقی کنترل‌شده داشته باشند؛ دکمه‌ها و فیلدها در صفحه کوچک قابل استفاده بمانند.
- وضعیت اتصال API نباید به‌تنهایی به معنی ورود معتبر یا مجوز دسترسی تلقی شود.
- داده نمایشی باید به‌وضوح از داده واقعی متمایز باشد؛ داده نمایشی هرگز نباید شبیه رکورد واقعی مشتری/مالی جلوه کند.
- دسترسی واقعی فقط از سوی بک‌اند اعمال می‌شود؛ پنهان کردن یک دکمه در رابط جایگزین مجوز سمت سرور نیست.

## ترتیب طراحی و تکمیل صفحات

### ۱. پوسته عمومی و ورود کارکنان
- [ ] نمای ورود کارکنان با خطای ورود، وضعیت در حال ارسال و پیام عمومی امن
- [ ] نمای تغییر گذرواژه اجباری
- [ ] نوار کناری واکنش‌گرا، حالت موبایل و امکان بستن منو
- [ ] هویت کاربر جاری، نقش، خروج و پیام پایان نشست
- [ ] وضعیت بارگذاری اولیه، خطای API و تلاش مجدد

**پذیرش:** در عرض موبایل و دسکتاپ قابل استفاده باشد؛ بدون نشست معتبر، صفحات داده‌ای نمایش داده نشوند.

### ۲. داشبورد
- [ ] شاخص‌ها با منبع و زمان به‌روزرسانی روشن
- [ ] نمودار وضعیت پرونده‌ها با حالت داده صفر
- [ ] پرونده‌های اخیر و وظایف نیازمند پیگیری
- [ ] نمایش مناسب برای نقش‌های دارای محدوده دسترسی متفاوت

**پذیرش:** هیچ عدد یا نمودار نمونه به‌عنوان آمار زنده نمایش داده نشود؛ تقسیم بر صفر و داده ناقص مدیریت شود.

### ۳. فهرست و جزئیات پرونده تسهیلات
- [ ] جست‌وجو، فیلتر وضعیت، پاک‌کردن فیلتر و حالت بدون نتیجه
- [ ] جزئیات پایه پرونده و مشتری مرتبط
- [ ] مراحل گردش کار و وضعیت هر مرحله
- [ ] اقدامات مجاز متناسب با نقش و وضعیت
- [ ] تاریخچه تغییرات و یادداشت پیگیری
- [ ] مدارک، نسخه‌های سند و نتیجه بررسی
- [ ] اشخاص پرونده، ضامن‌ها و مراحل فردی
- [ ] درخواست‌های ضمانت و پیگیری‌های مرتبط
- [ ] چاپ/خروجی با چیدمان مناسب چاپ

**پذیرش:** هر بخش باید شناسه پرونده واقعی API را استفاده کند؛ تغییر وضعیت فقط پس از تأیید پاسخ سرور در رابط منعکس شود.

### ۴. مشتریان و پروفایل مشتری
- [ ] فهرست با جست‌وجو و وضعیت مشتری
- [ ] فرم مشتری حقیقی و حقوقی با فیلدهای شرطی
- [ ] نمای پروفایل مشتری
- [ ] ویرایش اطلاعات پایه
- [ ] مدیریت چند شماره تماس و چند نشانی
- [ ] سوابق پرونده‌ها، خدمات و اسناد مرتبط
- [ ] بایگانی نرم و تأیید اقدام

**پذیرش:** اطلاعات حساس فقط برای نقش مجاز نمایش داده شود؛ خطای اعتبارسنجی فیلدبه‌فیلد قابل فهم باشد.

### ۵. وظایف و پیگیری
- [ ] فهرست، اولویت، مسئول، موعد و نشانگر تأخیر
- [ ] ایجاد وظیفه مرتبط با پرونده
- [ ] تغییر وضعیت و مشاهده تاریخچه
- [ ] فیلتر وظایف باز، تکمیل‌شده و عقب‌افتاده

**پذیرش:** تاریخ و ساعت با منطقه زمانی مشخص نمایش داده شوند؛ وظیفه خارج از محدوده دسترسی قابل مشاهده یا تغییر نباشد.

### ۶. خدمات، تعرفه‌ها و رسیدها
- [ ] فهرست خدمات و تعرفه‌های جاری
- [ ] ایجاد و ویرایش نام و تعرفه خدمت برای نقش مجاز
- [ ] ثبت رسید با مبلغ، تخفیف، دریافتی، مانده و روش پرداخت
- [ ] فهرست رسیدها با جست‌وجو و فیلتر
- [ ] نمایش روشن اینکه رسید داخلی لزوماً تأیید تراکنش کارت‌خوان نیست
- [ ] گزارش/چاپ رسید

**پذیرش:** محاسبات نهایی از پاسخ سرور بیایند؛ تکرار ارسال فرم رسید، رسید تکراری ایجاد نکند؛ رسید صادرشده بدون گردش اصلاح مجاز حذف یا بازنویسی نشود.

### ۷. گزارش‌ها
- [ ] شاخص‌های عملیاتی
- [ ] تفکیک مشتری، پرونده، وظیفه، ضمانت و رسید
- [ ] زمان تولید و محدوده دسترسی گزارش
- [ ] حالت داده صفر و خطای دریافت
- [ ] چاپ یا خروجی قابل اتکا

**پذیرش:** ارقام گزارش با API و محدوده مجاز نقش همخوان باشند؛ جمع‌ها و درصدها برای داده صفر معتبر بمانند.

### ۸. تنظیمات و مدیریت
- [ ] تغییر گذرواژه
- [ ] وضعیت اتصال بک‌اند و آزمون اتصال
- [ ] اطلاعات کاربر و نقش جاری
- [ ] نمایش امن وضعیت سرویس‌ها، بدون افشای secret یا جزئیات زیرساخت حساس
- [ ] صفحات مدیریت کاربران/نقش‌ها در صورت تأیید دامنه محصول

**پذیرش:** آزمون اتصال فقط سلامت API را گزارش کند و به‌عنوان احراز هویت یا مجوز کاربر معرفی نشود؛ هیچ secret در رابط نمایش داده نشود.

## ترتیب اجرای فنی

1. ممیزی تطبیق صفحه‌های موجود با این فهرست و حذف/علامت‌گذاری هر داده نمایشی.
2. تثبیت پوسته مشترک، واکنش‌گرایی، حالت‌های بارگذاری/خطا و دسترس‌پذیری فرم‌ها.
3. تکمیل طراحی فهرست و جزئیات پرونده، سپس پروفایل مشتری.
4. تکمیل وظایف، خدمات/رسیدها و گزارش‌ها.
5. تکمیل تنظیمات و نمایش صریح وضعیت اتصال/نشست.
6. آزمون هر صفحه در اندازه دسکتاپ و موبایل و با نقش‌های مختلف.
7. سپس اتصال نهایی و آزمون سرتاسری؛ استقرار عملیاتی پس از تکمیل معیارهای پذیرش.

## تعریف «طراحی تمام‌شده»

طراحی زمانی پذیرفته می‌شود که همه صفحه‌های لازم و حالت‌های کلیدی آن‌ها مشخص باشند، ناوبری بین صفحات بدون بن‌بست باشد، فرم‌ها و جدول‌ها در اندازه‌های مختلف قابل استفاده باشند، متن‌های وضعیت و خطا روشن باشند و هیچ داده آزمایشی با داده واقعی اشتباه گرفته نشود. این تعریف مستقل از آماده‌بودن بک‌اند و استقرار است.
