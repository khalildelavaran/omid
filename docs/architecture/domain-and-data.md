# مدل دامنه و داده

## 1. موجودیت‌های اصلی

این مدل مفهومی است؛ فیلدها و قیود نهایی باید با فرایند واقعی سازمان بازبینی شوند.

### Customer
- شناسه داخلی UUID
- نوع مشتری: حقیقی/حقوقی
- نام/نام سازمان و شناسه‌های موردنیاز قانونی
- راه‌های تماس و وضعیت تأیید آن‌ها
- وضعیت مشتری و منبع آشنایی
- زمان ایجاد/به‌روزرسانی و کاربر ایجادکننده

اطلاعات هویتی بسیار حساس را فقط در صورت ضرورت جمع‌آوری کنید. شماره‌های هویتی و تماس در لاگ عمومی یا ابزارهای تحلیلی ثبت نشوند.

### Lead
سرنخ بالقوه، منبع جذب، وضعیت، مسئول پیگیری و نتیجه تبدیل. اگر سازمان مفهوم سرنخ ندارد، این ماژول را می‌توان به فاز بعد منتقل کرد.

### Case
پرونده عملیاتی مرتبط با یک مشتری؛ شامل شماره قابل‌نمایش یکتا، نوع، وضعیت، مسئول، اولویت، تاریخ‌های کلیدی و ارجاع‌ها.

### LoanApplication
- مشتری و پرونده مرتبط
- نوع محصول/تسهیلات
- مبلغ درخواستی و واحد پول
- مدت و شرایط پیشنهادی، در صورت نیاز
- وضعیت و مرحله جاری
- نتیجه بررسی، تصمیم‌گیرنده و زمان تصمیم
- ارجاع به اسناد موردنیاز

تصمیم نهایی باید از مسیر گردش‌کار و بر اساس مجوز ثبت شود؛ تغییر مستقیم status از UI مجاز نیست.

### WorkflowTask / Assignment
- نوع وظیفه، پرونده مرجع، مسئول/گروه مسئول
- وضعیت، اولویت، موعد و SLA
- ایجادکننده، زمان ارجاع و علت
- تاریخچه انتقال و تکمیل

### Document
- شناسه، پرونده/مشتری مرتبط، نوع سند
- کلید ذخیره‌سازی خصوصی، اندازه، MIME type و checksum
- نسخه، وضعیت بررسی، بارگذار و زمان
- طبقه‌بندی محرمانگی و سیاست نگهداری

محتوای فایل در دیتابیس relational ذخیره نشود مگر دلیل فنی مشخصی وجود داشته باشد. فایل‌ها نباید با URL عمومی و دائمی قابل‌دسترسی باشند.

### Communication
کانال، گیرنده/مشتری، قالب یا نوع پیام، وضعیت ارسال، شناسه ارائه‌دهنده و زمان‌ها. محتوای OTP و اسرار احراز هویت هرگز در تاریخچه پیام یا لاگ قرار نگیرد.

### Invoice / PaymentRecord
برای ثبت فاکتور و وضعیت پرداخت. برای جلوگیری از ادعای حسابداری کامل، این مدل در فاز اولیه دفتر کل دوبل و reconciliation را پوشش نمی‌دهد. منبع حقیقت پرداخت باید مشخص باشد و callbackها idempotent پردازش شوند.

### AuditEvent
- actor (کاربر یا سیستم)
- action، entity type و entity id
- timestamp، correlation/request id
- نتیجه، علت/توضیح و تغییرات مجازِ قبل/بعد
- metadata محدود و پاک‌سازی‌شده

از ذخیره رمز، OTP، session cookie، access token یا محتوای کامل سند در audit event خودداری شود.

## 2. ارتباط‌های کلیدی

```text
Customer 1 --- N Case
Customer 1 --- N LoanApplication
Case     1 --- N WorkflowTask
Case     1 --- N Document
Case     1 --- N Communication
LoanApplication 1 --- N Document
User/Team 1 --- N Assignment
Actor    1 --- N AuditEvent
```

ارتباط دقیق LoanApplication با Case می‌تواند یک‌به‌یک یا یک‌به‌چند باشد؛ این تصمیم به فرایند شرکت وابسته است.

## 3. قواعد یکپارچگی

- از UUID یا شناسه‌های غیرقابل‌حدس برای منابع خارجی استفاده شود؛ شماره پرونده قابل‌خواندن جداگانه تولید شود.
- از حذف فیزیکی مشتری/پرونده مالی پس از ایجاد سابقه پرهیز شود؛ سیاست archive/retention و حذف قانونی تعریف شود.
- مبلغ‌ها با Decimal و واحد پول صریح ذخیره شوند؛ از float استفاده نشود.
- تاریخ‌ها در UTC ذخیره و در رابط کاربر به منطقه زمانی سازمان تبدیل شوند.
- تغییر وضعیت با state transition معتبر انجام شود؛ انتقال نامعتبر رد شود.
- عملیات چندمرحله‌ای دیتابیس در transaction اجرا شود.
- callbackهای بیرونی، ایجاد پرداخت و ارسال پیام با کلید idempotency یا شناسه رویداد از پردازش تکراری محافظت شوند.
- تغییرات مجوز، مالک پرونده، مبلغ و تصمیم تسهیلات ممیزی شوند.

## 4. حریم خصوصی و نگهداری

برای هر دسته داده، هدف جمع‌آوری، نقش‌های مجاز، مدت نگهداری و روش حذف/ناشناس‌سازی تعیین شود. داده‌های محیط توسعه باید مصنوعی باشند؛ داده واقعی مشتری به محیط توسعه یا تست کپی نشود مگر با فرایند مجاز و ناشناس‌سازی معتبر.

## 5. مهاجرت و تغییر schema

- migrationهای Django در Git ثبت شوند.
- تغییرات مخرب schema در چند مرحله deploy شوند.
- پیش از migrationهای حساس، backup و روش rollback/restore آزمایش شود.
- داده‌های موجود پیش از افزودن constraintهای سخت‌گیرانه پاک‌سازی و اعتبارسنجی شوند.
