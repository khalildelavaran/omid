# API و یکپارچه‌سازی‌ها

## 1. قرارداد API

- REST/JSON با پیشوند نسخه‌دار، برای مثال `/api/v1/`.
- استفاده از HTTP status codeهای درست و ساختار خطای ثابت.
- pagination برای فهرست‌ها، فیلترهای مجاز و مرتب‌سازی allowlistشده.
- validation در serializer؛ قواعد دامنه در service layer.
- عملیات حساس با مجوز backend و ثبت audit.
- schema مستندشده (OpenAPI) پس از ایجاد endpointها تولید و در CI اعتبارسنجی شود.
- هر endpoint باید مشخص کند چه نقش‌هایی و چه scope داده‌ای اجازه دسترسی دارند.

نمونه شکل خطا:

```json
{
  "error": {
    "code": "validation_error",
    "message": "ورودی نامعتبر است.",
    "details": {
      "field": ["مقدار قابل قبول نیست."]
    }
  }
}
```

نمونه صرفاً قراردادی است و endpoint واقعی را توصیف نمی‌کند.

## 2. گروه endpointهای پیشنهادی

| دامنه | مسیرهای پیشنهادی |
|---|---|
| هویت | `/api/v1/auth/csrf/`, `/api/v1/auth/login/`, `/api/v1/auth/me/`, `/api/v1/auth/logout/`, `/api/v1/auth/change-password/` |
| مشتریان | `/api/v1/customers/`, `/api/v1/customers/{id}/` |
| پرونده‌ها | `/api/v1/cases/`, `/api/v1/cases/{id}/` |
| تسهیلات | `/api/v1/applications/`, `/api/v1/applications/{id}/events/`, `/api/v1/applications/{id}/notes/` |
| ضمانت | `/api/v1/guarantees/`, `/api/v1/guarantees/{id}/` (ثبت و مشاهده درخواست؛ درخواست‌دهنده می‌تواند با مشتری پرونده متفاوت باشد، اما هر دو باید در محدوده دسترسی کاربر باشند) |
| وظایف | `/api/v1/tasks/`, `/api/v1/tasks/{id}/`, `/api/v1/tasks/{id}/assign/`, `/api/v1/tasks/{id}/events/`, `/api/v1/tasks/{id}/notes/`, `/api/v1/tasks/summary/`; فیلتر `overdue=true/false` و تاریخچه تغییرات (واگذاری فقط برای مدیر سامانه) |
| اسناد | `/api/v1/documents/`, `/api/v1/documents/{id}/download/`, `/api/v1/documents/{id}/review/`, `/api/v1/documents/{id}/replace/` (فایل خصوصی، PDF/JPEG/PNG، حداکثر ۱۰ مگابایت؛ جایگزینی نسخه بدون حذف سابقه) |
| ممیزی | `/api/v1/audit-events/` (فقط‌خواندنی برای مدیر سامانه و حسابرس) |
| گزارش | `/api/v1/reports/operations/` (هنوز پیاده‌سازی نشده) |

مسیرهای هویت، مشتریان، تسهیلات، وظایف، ضمانت، ممیزی و API اولیه اسناد در backend فعلی پیاده‌سازی شده‌اند؛ مسیرهای گزارش و API خدمات/رسید هنوز پیاده‌سازی نشده‌اند.

## 3. یکپارچه‌سازی پیامک

یک interface داخلی تعریف شود، مثلاً `SmsProvider.send(to, template, variables, idempotency_key)`. جزئیات API ارائه‌دهنده فقط داخل adapter قرار گیرد. قابلیت‌های لازم:
- timeout و retry محدود با backoff
- ثبت شناسه پیام و وضعیت تحویل، در صورت پشتیبانی
- قالب‌های تأییدشده و کنترل دسترسی به ارسال انبوه
- حذف OTP و اطلاعات حساس از لاگ
- جلوگیری از ارسال تکراری در retry

## 4. پرداخت و فاکتور

پیش از اتصال، منبع حقیقت مبلغ و وضعیت پرداخت مشخص شود. callback باید امضای/اعتبارسنجی ارائه‌دهنده را بررسی کند، مبلغ و شناسه سفارش را تطبیق دهد و idempotent باشد. وضعیت پرداخت فقط بر اساس redirect مرورگر یا پارامتر قابل‌دست‌کاری کلاینت نهایی نشود. اطلاعات کارت یا رمز بانکی ذخیره نشود.

## 5. امضای الکترونیکی

قبل از انتخاب ارائه‌دهنده، نوع امضا و اعتبار حقوقی موردنیاز، هویت امضاکننده، timestamp، تمامیت سند، شواهد رضایت و نگهداری سوابق با مسئول حقوقی/انطباق تعیین شود. OTP به‌تنهایی نباید بدون بررسی الزامات، معادل امضای معتبر فرض شود.

## 6. الگوی اجرای کارهای خارجی

برای ارسال پیام، پردازش فایل یا callback:
- عملیات دامنه و ثبت intent در دیتابیس با transaction انجام شود.
- کار خارجی در پس‌زمینه اجرا شود، اگر نیاز عملی وجود دارد.
- retry محدود و idempotency تعریف شود.
- وضعیت pending/succeeded/failed قابل مشاهده باشد.
- خطاهای ارائه‌دهنده به کاربر داخلی به‌شکل قابل‌اقدام نمایش داده شوند، بدون افشای اسرار فنی.
