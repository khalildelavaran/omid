# API و یکپارچه‌سازی‌ها

## 1. قرارداد API

- REST/JSON با پیشوند نسخه‌دار، برای مثال `/api/v1/`.
- استفاده از HTTP status codeهای درست و ساختار خطای ثابت.
- pagination برای فهرست‌ها، فیلترهای مجاز و مرتب‌سازی allowlistشده.
- validation در serializer؛ قواعد دامنه در service layer.
- عملیات حساس با مجوز backend و ثبت audit.
- schema ماشین‌خوان OpenAPI از مسیر `/api/v1/schema/` تولید می‌شود؛ این مسیر فقط برای کارکنان دارای نقش داخلی قابل دسترسی است.
- هر endpoint باید مشخص کند چه نقش‌هایی و چه scope داده‌ای اجازه دسترسی دارند.

نمونه شکل خطا:

```json
{
  "error": {
    "code": "validation_error",
    "message": "ورودی نامعتبر است.",
    "details": {
      "field": ["مقدار قابل قبول نیست."]
    }
  }
}
```

نمونه صرفاً قراردادی است و endpoint واقعی را توصیف نمی‌کند.

## 2. گروه endpointهای پیشنهادی

| دامنه | مسیرهای پیشنهادی |
|---|---|
| مستندات API | `/api/v1/schema/` (OpenAPI JSON، فقط کارکنان داخلی) |
| هویت | `/api/v1/auth/csrf/`, `/api/v1/auth/login/`, `/api/v1/auth/me/`, `/api/v1/auth/logout/`, `/api/v1/auth/change-password/` |
| مشتریان | `/api/v1/customers/`, `/api/v1/customers/{id}/` |
| پرونده‌ها | `/api/v1/cases/`, `/api/v1/cases/{id}/` |
| تسهیلات | `/api/v1/applications/`, `/api/v1/applications/{id}/events/`, `/api/v1/applications/{id}/notes/` |
| ضمانت | `/api/v1/guarantees/`, `/api/v1/guarantees/{id}/`, `/api/v1/guarantees/{id}/transition/`, `/api/v1/guarantees/{id}/events/`؛ رد فقط با تأییدکننده اعتباری و دلیل اجباری، تکمیل فقط با نقش مالی |
| خدمات و رسید | `/api/v1/services/catalog/`, `/api/v1/services/receipts/`؛ مدیریت تعرفه فقط برای مدیر سامانه، ثبت رسید برای نقش‌های داخلی مجاز، مبالغ در سمت سرور محاسبه می‌شوند، رسید حذف/ویرایش نمی‌شود و `Idempotency-Key` برای جلوگیری از ثبت تکراری پشتیبانی می‌شود |
| وظایف | `/api/v1/tasks/`, `/api/v1/tasks/{id}/`, `/api/v1/tasks/{id}/assign/`, `/api/v1/tasks/{id}/events/`, `/api/v1/tasks/{id}/notes/`, `/api/v1/tasks/summary/`; فیلتر `overdue=true/false` و تاریخچه تغییرات (واگذاری فقط برای مدیر سامانه) |
| اسناد | `/api/v1/documents/`, `/api/v1/documents/{id}/download/`, `/api/v1/documents/{id}/review/`, `/api/v1/documents/{id}/replace/` (فایل خصوصی، PDF/JPEG/PNG، حداکثر ۱۰ مگابایت؛ جایگزینی نسخه بدون حذف سابقه) |
| ممیزی | `/api/v1/audit-events/` (فقط‌خواندنی برای مدیر سامانه و حسابرس) |
| گزارش | `/api/v1/reports/operations/` (فقط‌خواندنی؛ آمار با محدوده دسترسی نقش فعلی، شامل مشتریان، پرونده‌ها، وظایف، ضمانت و رسیدهای خدمات) |

مسیرهای هویت، مشتریان، تسهیلات، وظایف، ضمانت، خدمات/رسید، ممیزی، گزارش عملیاتی و API اولیه اسناد در backend فعلی پیاده‌سازی شده‌اند. گزارش عملیاتی read-only است و برای کارشناسان به رکوردهای تخصیص‌یافته محدود می‌شود. ثبت رسید در این مرحله ثبت داخلی اطلاعات دریافت‌شده است و تأیید پرداخت از درگاه بانکی یا POS را انجام نمی‌دهد.

### پراکسی هم‌مبدأ از Cloudflare Worker به Django

- مسیرهای `/api/*` در Worker فقط وقتی به بک‌اند فرستاده می‌شوند که متغیر `OMID_API_ORIGIN` تنظیم شده باشد.
- مقدار این متغیر باید یک origin خالص HTTPS باشد؛ مسیر، query string، username/password و HTTP پذیرفته نمی‌شوند.
- Worker کوکی نشست و هدر CSRF را عبور می‌دهد، cache را برای پاسخ‌های API غیرفعال می‌کند و redirectهای همان origin را به دامنهٔ Worker برمی‌گرداند.
- مقدار `OMID_API_ORIGIN` هنوز در Worker پیکربندی نشده و origin عملیاتی Django در دسترس نیست؛ بنابراین این پراکسی فعلاً زیرساخت آماده‌شده است و رابط همچنان داده‌های نمایشی/localStorage را به کار می‌برد.
- فعال‌کردن همگام‌سازی نیازمند استقرار Django، تنظیم دامنه و CSRF، سپس پیاده‌سازی ورود کارکنان و adapterهای صریح برای نگاشت مدل‌های رابط به serializerهای API است. داده‌های محلی نباید خودکار یا بدون بازبینی به پایگاه داده منتقل شوند.

## 3. یکپارچه‌سازی پیامک

یک interface داخلی تعریف شود، مثلاً `SmsProvider.send(to, template, variables, idempotency_key)`. جزئیات API ارائه‌دهنده فقط داخل adapter قرار گیرد. قابلیت‌های لازم:
- timeout و retry محدود با backoff
- ثبت شناسه پیام و وضعیت تحویل، در صورت پشتیبانی
- قالب‌های تأییدشده و کنترل دسترسی به ارسال انبوه
- حذف OTP و اطلاعات حساس از لاگ
- جلوگیری از ارسال تکراری در retry

## 4. پرداخت و فاکتور

پیش از اتصال، منبع حقیقت مبلغ و وضعیت پرداخت مشخص شود. callback باید امضای/اعتبارسنجی ارائه‌دهنده را بررسی کند، مبلغ و شناسه سفارش را تطبیق دهد و idempotent باشد. وضعیت پرداخت فقط بر اساس redirect مرورگر یا پارامتر قابل‌دست‌کاری کلاینت نهایی نشود. اطلاعات کارت یا رمز بانکی ذخیره نشود.

## 5. امضای الکترونیکی

قبل از انتخاب ارائه‌دهنده، نوع امضا و اعتبار حقوقی موردنیاز، هویت امضاکننده، timestamp، تمامیت سند، شواهد رضایت و نگهداری سوابق با مسئول حقوقی/انطباق تعیین شود. OTP به‌تنهایی نباید بدون بررسی الزامات، معادل امضای معتبر فرض شود.

## 6. الگوی اجرای کارهای خارجی

برای ارسال پیام، پردازش فایل یا callback:
- عملیات دامنه و ثبت intent در دیتابیس با transaction انجام شود.
- کار خارجی در پس‌زمینه اجرا شود، اگر نیاز عملی وجود دارد.
- retry محدود و idempotency تعریف شود.
- وضعیت pending/succeeded/failed قابل مشاهده باشد.
- خطاهای ارائه‌دهنده به کاربر داخلی به‌شکل قابل‌اقدام نمایش داده شوند، بدون افشای اسرار فنی.


## 7. اتصال کارت‌خوان از طریق RS-232

### مرزبندی معماری

Cloudflare Worker و سرور Django به درگاه سریال رایانهٔ کاربر دسترسی مستقیم ندارند. اتصال فیزیکی باید روی همان رایانه‌ای اجرا شود که کارت‌خوان با کابل RS-232/USB-Serial به آن وصل است؛ بنابراین یک **عامل محلی (POS Bridge)** لازم است. این عامل فقط از پروتکل رسمی و مستند مدل کارت‌خوان پشتیبانی می‌کند و نباید با حدس‌زدن فرمان‌های سریال یا مهندسی معکوس پروتکل مالی کار کند.

جریان پیشنهادی:

1. رابط امید از backend یک شناسهٔ یکتای درخواست پرداخت می‌گیرد؛ مبلغ و ارز/واحد پول از سمت سرور تعیین می‌شوند.
2. عامل محلیِ نصب‌شده و مورد اعتماد، درخواست را با شناسهٔ یکتا دریافت می‌کند و قبل از ارسال به کارت‌خوان، مدل/پورت/وضعیت اتصال را بررسی می‌کند.
3. عامل فرمان پرداخت را طبق مستندات سازنده ارسال می‌کند و پاسخ خام سریال را فقط در لاگ تشخیصیِ پالایش‌شده نگه می‌دارد؛ اطلاعات کارت، رمز و داده‌های حساس نباید ثبت شوند.
4. نتیجهٔ موفق تنها وقتی ثبت می‌شود که پاسخ معتبر کارت‌خوان شامل شناسهٔ تراکنش و مبلغ مطابق باشد؛ timeout یا قطع ارتباط به معنی پرداخت موفق نیست.
5. backend نتیجه را به‌صورت idempotent ثبت می‌کند. تکرار همان شناسه نباید پرداخت دوم یا رسید دوم بسازد؛ وضعیت مبهم باید به استعلام/تطبیق نیاز داشته باشد، نه retry کور.

### قرارداد و امنیت عامل محلی

- عامل محلی باید روی \`localhost\`/loopback گوش دهد؛ به شبکهٔ عمومی bind نشود.
- فقط originهای مجاز رابط اجازهٔ درخواست داشته باشند؛ CORS به‌تنهایی احراز هویت نیست. برای هر نصب، pairing/secret محلی و چرخش آن لازم است.
- مبلغ را از payload قابل‌تغییر مرورگر به‌تنهایی نپذیرد؛ شناسهٔ intent را از backend بگیرد و مبلغ را از پاسخ معتبر backend تطبیق دهد.
- عملیات پرداخت دارای timeout، شناسهٔ correlation، حالت‌های \`pending\`, \`succeeded\`, \`declined\`, \`unknown\` و ثبت رویداد ممیزی باشد.
- قطع برق/پورت پس از ارسال فرمان باید \`unknown\` ایجاد کند تا وضعیت با گزارش کارت‌خوان یا فرایند تطبیق روشن شود؛ پرداخت را خودکار دوباره ارسال نکن.
- اطلاعات کارت، PIN، track data یا کلیدهای پرداخت هرگز به امید، Django، log یا مرورگر منتقل/ذخیره نشوند.
- فقط از مدل کارت‌خوان و پروتکل رسمی تأییدشده توسط فروشنده استفاده شود. تنظیماتی مانند baud rate، parity و فرمان‌ها تا تعیین مدل دقیق دستگاه عمداً ثابت نشده‌اند.

### مسیرهای API پیشنهادی (هنوز پیاده‌سازی نشده‌اند)

- \`POST /api/v1/payment-intents/\`: ایجاد intent برای رسید/فاکتور موجود؛ مبلغ از محاسبهٔ سمت سرور.
- \`GET /api/v1/payment-intents/{id}/\`: خواندن وضعیت intent در محدودهٔ مجوز کاربر.
- \`POST /api/v1/payment-intents/{id}/terminal-result/\`: ثبت نتیجهٔ عامل محلی با احراز هویت عامل، idempotency و تطبیق مبلغ/شناسهٔ تراکنش.
- \`POST /api/v1/payment-intents/{id}/reconcile/\`: ثبت نتیجهٔ تطبیق توسط نقش مالی؛ ثبت ممیزی الزامی.

قبل از پیاده‌سازی این endpointها باید مدل دقیق کارت‌خوان، سیستم‌عامل رایانهٔ متصل، مستندات رسمی پروتکل، نحوهٔ احراز هویت عامل و فرایند تسویهٔ مالی مشخص شوند. تا آن زمان ثبت مبلغ دریافتی در ماژول خدمات، فقط **ثبت داخلی** است و اثبات تراکنش کارت‌خوان محسوب نمی‌شود.
