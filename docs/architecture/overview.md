# معماری کلان سامانه امید

## 1. هدف و محدوده

سامانه امید یک CRM عملیاتی برای شرکت مالی است که کارمندها بتوانند مشتریان، سرنخ‌ها، درخواست‌های وام/تسهیلات، اسناد، وظایف، مکاتبات و تأییدها را در یک سامانه داخلی مدیریت کنند. در صورت نیاز، پنل مشتریان برای ثبت درخواست و پیگیری وضعیت در نظر گرفته می‌شود.

### داخل محدوده نسخه اولیه
- کاربران داخلی، نقش‌ها و مجوزها
- پرونده یکتای مشتری و اطلاعات تماس
- ثبت درخواست و پرونده تسهیلات
- گردش‌کار، ارجاع، وظیفه و یادآوری
- بارگذاری و مدیریت اسناد
- ثبت یادداشت و تاریخچه رویدادها
- گزارش‌های عملیاتی و مدیریتی پایه
- نقاط اتصال قابل‌تعویض برای پیامک و پرداخت/فاکتور
- پنل مشتریان با دسترسی محدود به اطلاعات متعلق به همان مشتری، در فاز تعریف‌شده

### خارج از محدوده اولیه مگر با تصمیم صریح
- هسته بانکی یا اتصال مستقیم به حساب بانکی
- تصمیم‌گیری اعتباری خودکار و مدل امتیازدهی
- دفتر کل و حسابداری کامل
- امضای حقوقی معتبر بدون ارزیابی مقررات و ارائه‌دهنده مربوط
- معماری microservices؛ در نسخه اولیه پیچیدگی آن توجیه نشده است.

## 2. اصول معماری

- **Modular Monolith:** یک برنامه Django با مرزهای دامنه‌ای روشن.
- **API-first:** منطق کسب‌وکار در backend باشد؛ UI منطق مجوز را دور نزند.
- **Secure by default:** حداقل دسترسی، احراز هویت قوی، ثبت ممیزی و مدیریت امن اسرار.
- **Auditability:** وضعیت‌های مهم پرونده با عامل، زمان و علت قابل ردیابی باشند.
- **Replaceable integrations:** پیامک، پرداخت و امضا پشت interface/adaptor قرار بگیرند.
- **Incremental delivery:** هر فاز قابل‌آزمون و قابل‌استفاده باشد.

## 3. نمای منطقی

```text
کاربر داخلی / مشتری
        |
   HTTPS / Reverse Proxy
        |
   Web UI (Next.js)
        |
   REST API (Django REST Framework)
        |
  +-----+-----------------------------+
  |     |       |       |             |
Identity CRM  Workflow Loans       Documents
  |     |       |       |             |
  +-----+-------+-------+-------------+
                    |
              PostgreSQL
                    |
      Private Object/File Storage
                    |
       Integration Adapters
       SMS / Payment / E-sign
```

این دیاگرام نمای منطقی است، نه الزاماً تعداد سرویس‌ها یا ماشین‌های مستقل.

## 4. فناوری پیشنهادی

- Python 3.x با نسخه پشتیبانی‌شده و تثبیت‌شده در زمان شروع
- Django و Django REST Framework
- PostgreSQL
- Next.js + TypeScript برای رابط وب
- ذخیره‌سازی فایل خصوصی با مسیر/کلید غیرقابل‌حدس و کنترل دسترسی از backend
- Docker Compose برای توسعه و استقرار اولیه کنترل‌شده
- صف وظایف (مانند Celery و Redis) فقط زمانی اضافه شود که ارسال پیام، پردازش فایل یا کارهای زمان‌بر واقعاً به اجرای پس‌زمینه نیاز داشته باشند.

نسخه دقیق پکیج‌ها در فایل‌های dependency قفل خواهد شد؛ این سند به‌تنهایی نسخه‌ها را تعیین نمی‌کند.

## 5. ماژول‌های backend

پیشنهاد اولیه برای Django apps:
- `accounts`: کاربر، گروه‌ها، نقش‌ها، نشست‌ها و سیاست ورود
- `customers`: مشتری، راه‌های تماس، رضایت‌ها و تکراری‌یابی
- `leads`: سرنخ و منبع جذب، در صورت نیاز کسب‌وکار
- `cases`: پرونده عمومی و مالک/مسئول پرونده
- `loans`: درخواست و پرونده تسهیلات و وضعیت‌های مرتبط
- `workflow`: وظایف، ارجاع، مراحل و SLA
- `documents`: metadata، نسخه‌ها، طبقه‌بندی و دسترسی فایل
- `communications`: پیام‌ها و تاریخچه ارتباط
- `billing`: فاکتور/پرداخت‌های ثبت‌شده، نه دفتر کل کامل
- `audit`: رویدادهای ممیزی
- `reporting`: queryها و گزارش‌های عملیاتی

ماژول‌ها باید از طریق سرویس‌های دامنه‌ای و APIهای داخلی روشن با یکدیگر تعامل کنند؛ از وابستگی دوری و importهای چرخه‌ای پرهیز شود.

## 6. الگوی جریان درخواست

1. مرورگر درخواست HTTPS می‌فرستد.
2. لایه هویت نشست/توکن را اعتبارسنجی می‌کند.
3. مجوز endpoint و مجوز دسترسی به شیء/پرونده بررسی می‌شود.
4. serializer ورودی را اعتبارسنجی می‌کند.
5. سرویس دامنه عملیات را در تراکنش دیتابیس اجرا می‌کند.
6. رویداد ممیزی ثبت می‌شود؛ عملیات خارجی در صورت لزوم از طریق صف/الگوی outbox اجرا می‌شود.
7. پاسخ حداقلی و بدون داده حساس غیرضروری برگردانده می‌شود.

## 7. تصمیم‌های باز

این موارد پیش از انتشار باید با مالک محصول روشن شوند:
- آیا پنل مشتریان از روز اول لازم است؟
- شناسه یکتای مشتری و سیاست ادغام رکوردهای تکراری چیست؟
- مراحل دقیق بررسی و تصویب تسهیلات و حدود اختیار هر نقش چیست؟
- چه داده‌هایی اجباری/حساس هستند و دوره نگهداری آن‌ها چقدر است؟
- الزامات امضای الکترونیکی، نگهداری اسناد و قوانین حوزه قضایی چیست؟
- ارائه‌دهندگان پیامک، پرداخت و امضا کدام‌اند؟
