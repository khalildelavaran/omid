# استقرار، پشتیبان‌گیری و مشاهده‌پذیری

## 1. محیط‌ها

- **Local development:** داده مصنوعی و تنظیمات محلی؛ secretها از فایل محلی خارج از Git.
- **Test/CI:** دیتابیس و سرویس‌های ایزوله؛ بدون اطلاعات واقعی مشتری.
- **Production:** شبکه و دسترسی محدود، TLS، حساب‌های سرویس جداگانه و secretهای مدیریت‌شده.

تنظیمات هر محیط از کد جدا باشد. فایل `.env` حاوی اسرار نباید commit شود؛ فقط `.env.example` با مقادیر ساختگی در مخزن قرار گیرد.

## 2. استقرار اولیه

برای شروع می‌توان از Docker Compose در زیرساخت داخلی استفاده کرد:
- reverse proxy با TLS
- backend Django/ASGI یا WSGI
- frontend Next.js
- PostgreSQL در شبکه خصوصی
- فضای فایل خصوصی
- سرویس worker/queue در صورت اضافه‌شدن کارهای پس‌زمینه

این پیشنهاد برای شروع است و باید با ظرفیت، سیاست شبکه و الزامات پایداری سازمان هماهنگ شود. دیتابیس نباید مستقیم به اینترنت منتشر شود.

## 3. پیکربندی production

- `DEBUG=False`
- `SECRET_KEY` و credentialهای سرویس از secret store
- `ALLOWED_HOSTS` و originهای مجاز دقیق
- HTTPS، HSTS پس از بررسی درست بودن TLS، cookieهای امن
- کاربر دیتابیس با حداقل مجوز
- اجرای migration کنترل‌شده در فرایند release
- فایل‌های آپلودی خارج از مسیر عمومی web root
- محدودیت CPU/RAM و فضای ذخیره‌سازی
- ساعت سیستم همگام و منطقه زمانی مشخص

## 4. Backup و بازیابی

- برنامه backup منظم PostgreSQL و فایل‌ها با سیاست retention مصوب.
- رمزگذاری backup در حالت ذخیره و محدودیت دسترسی.
- نگهداری یک نسخه جدا از محیط اصلی طبق سیاست سازمان.
- تست دوره‌ای restore؛ موفق بودن job backup به‌تنهایی کافی نیست.
- RPO و RTO با مالک کسب‌وکار تعیین شوند؛ این سند عددی را از پیش فرض نمی‌کند.
- روش بازیابی شامل دیتابیس، اسناد، تنظیمات و کلیدهای لازم مستند شود، بدون قرار دادن خود کلیدها در سند.

## 5. لاگ و پایش

حداقل شاخص‌ها:
- نرخ خطای HTTP و latency
- خطاهای backend و اتصال دیتابیس
- طول صف و تعداد retryهای ناموفق، در صورت وجود worker
- وضعیت فضای دیسک و backup
- شکست ارسال پیام یا callbackهای نامعتبر
- رخدادهای ورود ناموفق و محدودیت نرخ

لاگ‌ها باید ساختاریافته باشند، correlation ID داشته باشند و اطلاعات هویتی/مالی غیرضروری را حذف یا ماسک کنند. token، رمز، OTP، cookie و محتویات سند را ثبت نکنید.

## 6. انتشار و بازگشت

- CI: lint، آزمون واحد/API، بررسی migration و dependency scan.
- نسخه منتشرشده باید قابل‌شناسایی باشد.
- migrationهای ناسازگار با نسخه قبلی به‌صورت مرحله‌ای انجام شوند.
- rollback کد به‌تنهایی کافی نیست اگر migration برگشت‌ناپذیر بوده؛ برای تغییرات داده، طرح بازیابی مشخص شود.
- انتشار در محیط آزمایشی و آزمون smoke پیش از production انجام شود.
